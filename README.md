# Atera Sync

Resolve Atera tickets generated by alerts when the underlying alerts are resolved.

## Tech

- Python 3.12
- httpx, pydantic, tenacity, typer
- Docker for packaging

## Setup

The API key is read from `.env` as `ATERA_API_KEY` and passed into Docker via `env_file`.

### Install (local)

If you have `uv`:

```bash
uv venv
uv pip install -e .
```

Otherwise:

```bash
python -m venv .venv
source .venv/bin/activate
pip install -e .
```

## One-off test (mandatory)

Local:

```bash
source .venv/bin/activate
atera-sync test
```

Docker:

```bash
docker compose run --rm atera-sync atera-sync test
```

This fetches tickets `9981` and `9956`, prints a redacted summary (ticket id, status, source, alert id), and saves full JSON to `fixtures/`.
If any request fails, it prints the status code + response body and exits nonzero.

If ticket fixtures do not include alert ids, fetch an alert by id and save a sample fixture:

```bash
atera-sync alert-sample <alert_id>
```

Export full open alerts list:

```bash
atera-sync alerts-export
```

## One-off run

Local:

```bash
source .venv/bin/activate
atera-sync run
```

Docker:

```bash
docker compose run --rm atera-sync atera-sync run
```

## Tests

```bash
pytest
```

Tests load fixtures from `fixtures/`. Run the test command first to populate ticket fixtures:

```bash
docker compose run --rm atera-sync atera-sync test
```

## Scheduling (outside container only)

### Linux cron (daily at 02:00)

```cron
0 2 * * * cd /home/master/Development/AteraAlertResolver && docker compose run --rm atera-sync atera-sync run >> sync.log 2>&1
```

### Windows Task Scheduler

Create a daily task at 02:00 with the action:

```
docker compose run --rm atera-sync atera-sync run
```

Set the “Start in” directory to:

```
C:\path\to\AteraAlertResolver
```

## Notes

- Alerts are listed with status `Open` and used to discover related ticket ids.
- Pagination uses `itemsInPage=50` and follows `nextLink` until empty, accumulating `items`.
- For each open alert, full alert details are fetched to extract linked `ticketId`.
- Alerts are considered actionable if alert status equals `open` (case-insensitive), with fallback to the list filter status when not present.
- Tickets are updated to `Resolved` only if not already in terminal states `Resolved`/`Closed`/`Merged`/`Deleted`.
- Each ticket is processed at most once per run even if multiple open alerts reference the same ticket.
