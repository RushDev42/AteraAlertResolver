Atera Alert Resolver Assessment

Review of the current repository against four criteria: portability, ease of scheduling, conformance with the current Atera API documentation, and operator-facing status visibility. The application is functional as a narrow CLI job, but it is not yet shaped like a durable scheduled service with operator tooling.

Criteria Review

Portability

2 / 5

The app can run on multiple hosts, but packaging and runtime paths are too dependent on launch context.

  • Issue: pyproject.toml has no [build-system], so editable install behavior depends on tool fallback behavior.
  • Issue: .env and fixtures/ are read and written from the current working directory, which is brittle for Task Scheduler, cron, and package installs.
  • Issue: docker-compose.yml bind-mounts the repo over /app, making container behavior depend on host path sharing and filesystem semantics.
  • Resolve: add an explicit build backend, move config and output paths behind CLI options or environment variables, and make Docker runnable without a source bind mount for production scheduling.

Scheduling Ease

2 / 5

The command is easy to invoke, but the unattended operating model is weak.

  • Issue: there is no cross-run lock or overlap protection; concurrent scheduled launches can process the same alert set at the same time.
  • Issue: comment creation happens before ticket status update, so a retry after partial failure can add duplicate comments.
  • Issue: scheduler guidance is basic and log-centric, without wrapper scripts, rotation, overlap policy, or clear failure markers for operations.
  • Resolve: add a lock file or OS mutex, make ticket changes idempotent across retries, and provide supported scheduler wrappers for Linux and Windows with explicit logging and retention.

Atera API Guidelines

4 / 5

The request model is broadly aligned with the published Atera v3 spec, but there are a few contract mismatches and undocumented assumptions. Authentication was updated after the original review; live token validation remains pending.

  • Issue: GET /api/v3/alerts/{alertId} is treated as success only on HTTP 200, while the current published Swagger response is 201.
  • Issue: alert-list filtering silently drops alertStatus after a 400, which hides contract drift instead of surfacing it.
  • Issue: ticket updates probe POST, PUT, then PATCH; the current docs publish POST and PUT, not PATCH.
  • Authentication update (October 12, 2026): the client reads ATERA_API_TOKEN and sends Authorization: Bearer <token>, as shown in Atera's token guide and its authentication example. The legacy X-API-KEY header is no longer used by this repository. Unit tests cover the request header; live Atera validation must be performed with a token in the deployment environment.
  • Aligned in the original review: pagination via items and nextLink, ticket comment payload shape, and {"TicketStatus":"Resolved"} updates.
  • Resolve: accept the documented alert-detail success code, remove or log the unfiltered fallback path, and tighten method usage to published endpoints only.

Status / Front End

2 / 5

There is no operator-facing UI or durable run-status surface. Status exists only as log output and fixture files.

  • Issue: the project is CLI-only, with no dashboard, run history view, or health endpoint.
  • Issue: progress is not presented as completed items, percentage, ETA, or active run state.
  • Issue: failures require raw log inspection, and there is no run ledger with last success, last failure, duration, or changed ticket count.
  • Resolve: persist each run to a structured store or JSON ledger and expose a small local status UI showing last run, current run, failure details, and recent updated tickets.

Recommended Next Steps

  • Stabilize the runtime contract first: explicit build backend, configurable paths, and production-safe Docker execution.
  • Make scheduling durable next: overlap protection, idempotent retry behavior, and wrapper scripts for cron and Task Scheduler.
  • Correct the documented Atera API mismatches, especially alert-detail success handling and undocumented method fallbacks.
  • Add a minimal operator surface last: structured run records plus a small HTML status page or lightweight local web app.
